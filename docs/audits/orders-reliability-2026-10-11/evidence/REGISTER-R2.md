## 0. Executive summary
The Orders problems are not one bug. They are five causal chains that all trace back to ONE systemic cause: **there is a single environment — the production database is also the preview, local-dev and AI-agent database — and the database has no deployment pipeline while code does.** Between 2026-09-07 and 09-11, three uncoordinated changes landed on that shared DB/code base (a date-guard trigger, a view repoint, and the PR #67 client rewrite of the orders data layer). The DB halves went live immediately; the matching code halves were stranded on an unmerged branch. Then on 2026-10-07 a GitHub-identity switch silently BLOCKED all deployments. On top, Supabase Free/Nano + a 10-connection pool turn the client's "download the whole order book" design into timeouts.
While auditing, two LIVE security holes were found (cross-tenant PII backups readable by any signup; cross-tenant stock/billing write RPCs).

Top unlocks (measured or reproduced): (1) security hotfix; (2) restore deploys (identity); (3) gate the orders query on settled filters + stop the anonymous seed (fixes wrong lists, C1/C2/C3, and wrong numbers on Dashboard/Finances/Products); (4) stop listing through the normalize_phone view / remove the full-book path (−90% DB CPU per open, C1/C3/C4); (5) ship scheduled-date postponement (C5); (6) one visible, Arabic error system that keeps data on screen; (7) environment separation + migrations-as-files with a drift gate (stops recurrence).

## 2. Causal chains (complaint → mechanism → measured attribution)

### CH-A "Wrong orders / chips don't match / numbers wrong" (C1, C2, C3; also Dashboard, Finances, Products, Reports)
1. Root: filter state seeds from `localStorage['schneiders_prefs_anonymous_orderFilters']` (use-order-filter-state.ts:33-48) before auth resolves; real saved filter applies one render later; React Query's fetch already started with the seed window and the follow-up `refetchQueries` JOINS the in-flight fetch when no data exists (query-core cancelRefetch only cancels with data). `filtersSettled` exists, never consumed (use-orders.ts:60).
2. The anonymous key is written by `/orders?status=` (dashboard card links, page.tsx:199-208) during the pre-auth render (PageGuard renders before auth, role-guard.tsx:84-89) and spreads the old seed → its dates are frozen at the first write (prod: one user's app opened on the **2026-09-11** window 9 times on Oct 9–10).
3. Triggers: every PWA launch, new tab, or reload >5 min after the last windowed fetch, for any user whose saved filter ≠ seed (SWR snapshot is per-tab, ≤5 min, and an All-dates book can't be stored: 9.4 M chars > quota).
4. Visible: All-dates user sees today's ~27–55 rows (or Sep 11 rows) under "All 5,095"; "No response 777" chip over "No orders found"; product chips derived from the wrong rows. Corrects only on focus after 30 s, a status change, or a date toggle → staff reload/toggle (prod logs show it; ~48 s to a usable list in one case).
5. Amplifiers: realtime + heartbeat delta admit rows by the *current* window ref, not the cache's actual window (realtime-batcher.ts:227-232, 288-291) → arbitrary rows trickle into the wrong list ("orders appear after some time"); realtime UPDATE replaces the row with the raw `orders` payload which has no `risk_data` → risk badges vanish (realtime-batcher.ts:150-161).
6. Cross-route blast (NEW-1): OrdersProvider is mounted at the root (app/layout.tsx:101), so Dashboard "/", Finances, Products ("best seller", sales sort), Reports, Analytics, Printing, Chat, global search and the cards' customer-intelligence (repeat-customer/duplicate badges) all compute from the windowed cache with no completeness check. Live example: Finances "cash collected" 108.8 M IQD complete vs 0 under a day window; 45% of repeat customers look first-time; 12% of 72-h duplicates missed.
Attribution: 100% client (PR #67, merged 09-10, deployed 09-11 00:24). Repro: r2-client/flow1.test.tsx S1–S8 (11/11) with real React 19.2.1 + RQ 5.96.2.

### CH-B "Slow to load / slow to switch to All dates / random failures" (C1, C3, part of C4)
1. Data model: client downloads the whole order book (count + 6 parallel 1,000-row OFFSET pages = 9.43 MB raw / ~3.1 MB gzip) through `v_orders_with_risk`; triggered by All-dates opens, refocus after 30 s, 2 s after every status change, hover-prefetch, and on every route because the provider is at the root.
2. DB regression (RC-2, 09-09, live-only migration from an unshipped branch): the view was repointed from `customer_risk` (0 rows, join eliminable) to `LEFT JOIN customer_trust ON normalize_phone(o.phone)=normalize_phone(ct.phone)` (plpgsql, non-indexable). Measured on current data, same SQL shape: full-book page 94 → 252 ms (×~3), exact HEAD count 32 → 175 ms (×5; PostgREST evaluates the view twice and the join can no longer be removed), 9.9 MB temp spill per page. Prod edge before/after: 09-08 p50 622 / p95 1,659 / 0 timeouts → 09-10 (view only) p50 1,206 / p95 2,793 → 10-10 (view + PR #67 traffic) p50 1,551 / p95 6,465 / 21 timeouts per day.
3. Capacity (RC-4, Free/Nano): one All-dates open = 7 concurrent heavy queries ≈ 1.6 s of CPU on ~1 core with a 10-connection pool → self-contention (page intrinsic 225 ms → edge 1,574 ms p50; trivial user_profiles 1.7 ms in PG → 310 ms at edge = queueing). Bursts after token refresh → 57014 statement timeouts (8 s) → HTTP 500.
4. Client error handling: postgrest-js retries GET 3× + React Query 2× → up to 84 requests per All-dates fan-out; after ~57 s a failed REFETCH flips `status:'error'` and the page renders an English "Failed to fetch orders" card INSTEAD of the cached list (page.tsx:825-836).
Attribution (measured): C3 switch-to-All p50 +929 ms since 09-08: RC-2 ≈63%, RC-3/RC-4/growth ≈37%; p95: RC-2 ≈24%, RC-3+RC-4 ≈76% (timeouts are post-PR-#67 bursts on Nano). C1 for a Today user: RC-2 ≈5–10%, queueing ≈90%. C2 (status chip switch) issues no DB query: 0% DB.
End-to-end (desktop, modelled from measured parts): cold /orders All-dates ≈6–7 s p50, ≥15 s or failure p95 (PG intrinsic ~7%, contention ~35%, network/geo ~30%, client 10–15%); Today→All 4.5–6 s p50; "/" LCP p75 8.0 s (TTFB 2.1 s from middleware auth in Mumbai + 673 KB br JS + dashboard RPC self-contended by the same user's full-book fan-out).

### CH-D "Search by phone / order ID doesn't find the order" (C4)
- Prod has NO server search (search_orders RPC is live but its caller is on the unshipped branch; that RPC is also un-normalized).
- Top-bar search (every route) filters the windowed cache with raw `phone.includes` (global-search.tsx:52,83-84): misses all `+9647…`-stored phones when typed as shown on the card (07…) — 37.8% of the main tenant's phones; never matches secondary phone or the internal number (#3879); result links go to `/orders?search=` which the page ignores.
- In-page search: escapes the window only by clearing dates → full-book refetch (CH-B slow path, timeout-prone); is ANDed with the active status/product chips and the chips don't show where hits are; `#7555`/`#3879` never match (`#` kept in the query); clearing the search silently resets the date filter to Today.
- Low reach: mobile search never widens window (≈1 mobile user); Persian digits; archive toggle dead; delivery_order_id/waseet_qr_id not loaded.
- Fix shape: one server-side, tenant-scoped, normalized search (both phones, '#'-stripped, order_id, sequence_number, delivery ids) independent of the date window, with per-status hit counts; drives top bar, page and `?search=`.

### CH-E "Changing the order date errors; the change-date feature doesn't show up" (C5)
