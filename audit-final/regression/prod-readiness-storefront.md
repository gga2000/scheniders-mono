## New observations (not in any prior source)

- **N-1 (now table row NEW-P1-01, Confirmed P0 by the Phase 1 critic): `charge_wallet_atomic` lets any tenant member credit their own wallet. Serious, P0-class.** The live definition (SQL `pg_get_functiondef`) checks membership but never checks `_amount > 0`. It computes `_new_balance := _current_balance - _amount` and writes it. `wallet` and `wallet_transactions` have no sign CHECK (only type and payment_method checks) and no guarding trigger (only `trg_log_wallet_notification`). `has_function_privilege('authenticated', …)` = true. Any signed-in member of tenant T, of any role, can POST `/rest/v1/rpc/charge_wallet_atomic {"_tenant_id":T,"_amount":-1000000}` and add 1,000,000 IQD to T's prepaid balance. That balance pays for platform order fees and subscription renewal (`apps/platform/app/api/cron/subscription-renew/route.ts:107`). Every legitimate caller is server-side with the service role (`apps/platform/lib/order-service.ts:158`, `lib/tenant.ts:362`, `cron/subscription-renew/route.ts:107`), so revoking EXECUTE from `authenticated` and adding `IF _amount <= 0 THEN RAISE` would not break the app. This is a HYPOTHESIS until exercised: it was derived from the function body, and nothing was run.
- **N-2: Admin wallet top-up has no permission tier, no audit log and no atomicity.** `apps/admin/app/api/billing/topup/route.ts:11-82` relies only on the middleware, so any `support_staff` can call it. It does not call `requireAdminPermission`, unlike impersonate or settings. It reads the balance (`:27-31`), writes `balance + amount` (`:46-52`), then inserts a transaction with no actor (`:63-71`). Concurrent top-ups or charges can lose updates, and no `admin_activity_logs` row records who credited the wallet.
- **N-3: Platform Sentry may be inert. HYPOTHESIS.** `apps/platform` has `sentry.server.config.ts`, `sentry.edge.config.ts` and `sentry.client.config.ts`, plus `withSentryConfig` (`next.config.ts:146-148`). It has **no** `instrumentation.ts` or `instrumentation-client.ts`, and `@sentry/nextjs` is `^10.40.0`. From v8 on, the server and edge configs load only through `instrumentation.ts` `register()`. If so, server-side errors are not reported even on the platform, and observability is weaker than F-25 assumes. Verify in the Sentry project.
- **N-4: `POST /api/domains/verify` is unauthenticated and uses the service role.** `apps/platform/app/api/domains/verify/route.ts:5-61` takes any `domain_id` without auth, reads `tenant_domains` with the service client, and sets `verified=true` when the CNAME merely *contains* `vercel` or `scheniders.com` (`:28-33`). Impact is limited because the row must already exist and DNS must resolve. It is still the only non-auth platform API route that writes with the service role, and it has no Zod or rate limit.
- **N-5 (Confirmed P0 by the Phase 1 critic; table row NEW-P1-04 in master-ledger): `qc-evidence` lets any signed-in user delete objects across tenants.** "Authenticated delete qc-evidence" is `DELETE TO authenticated USING (bucket_id='qc-evidence')` (SQL). This is broader than B-07's read and upload concern: evidence used for supplier disputes can be erased by another tenant. It belongs to the same fix as B-07.
- **N-6: The storage lockdown migration has sat unapplied since May.** `packages/supabase/migrations/20260518000003_storage_lockdown.sql` would close B-07, B-08, F-22, F-23 and F-24. It is gated on uploader code adding a `${tenantId}/` path prefix (`:22-33`). The gate is now partly stale: `vault_backups` was already handled by role, and `tenant-assets` already enforces the tenant prefix live. The remaining work: qc-evidence and product-images uploaders need the prefix, then apply the migration. Until then, anonymous deletion of product images (F-23) is live.
